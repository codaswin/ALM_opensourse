# Desktop Implementation Status

## Implemented and locally verified

- Runtime profiles preserve hosted-server behavior and make desktop mode local-first.
- Desktop identity, per-launch loopback authentication, SQLite domain/runtime state, app-data paths, migrations, backup-before-migrate, and OS-keyring-only credential values are implemented.
- Legacy notification, episodic, and semantic-memory ownership gaps are migrated and user-scoped; working-memory keys and FAISS stores are isolated.
- RAG snapshots use cross-platform locking, versioned metadata, bounded generations, dimension checks, and metadata-driven rebuild.
- Tauri owns a frozen FastAPI sidecar on a dynamic loopback port, sends its launch token through stdin, supports single-instance focus, and stops the child on exit.
- The React/Vite UI handles desktop bootstrap, local-owner onboarding, capability-aware navigation, structured startup failures, and the safety pause/resume switch.
- **Update (2026-08-21): this repository is now desktop-only.** The self-hosted/multi-user dashboard login (username/password, cookie sessions, CSRF, login audit, admin user-invite) and the `deploy/`/Docker Compose deployment infrastructure were removed — self-hosted deployment is maintained in a separate repository going forward. `RuntimeMode.SERVER` stays declared as a concept, but a non-desktop request now gets a `501` rather than being authenticated, since login was its only implementation. The bullet below (Linux PyInstaller sidecar working without Python/PostgreSQL/Redis services) predates this and remains accurate for desktop mode.
- The Linux PyInstaller sidecar starts from a clean application-data directory and completes migrations and shutdown without Python, PostgreSQL, or Redis services.
- `GET /diagnostics` reports live status (not just "the process started") for the database, runtime-state store, scheduler, per-user vector store, credential store, and kill switch, surfaced in a new Diagnostics tab — addresses the audit's "no diagnostic view" gap.
- `POST /credentials/{platform_id}/test` actually calls Anthropic, OpenAI, Composio, GitHub, Reddit, and Product Hunt with the saved credential and reports `connected` / `invalid` / `missing` / `unavailable`, wired to a "Test connection" button in Connections — addresses the audit's "credential status means 'stored', not 'verified'" gap for every platform with a practical live check. LinkedIn itself (an OAuth-connected account through Composio) and Hermes/Brave/X have no independent live check yet.
- Native application icons exist (`src-tauri/icons/`, generated from `app-icon.svg`, an original abstract multi-agent mark — not any third-party logo) and are wired into `bundle.icon`; `tauri.conf.json`'s bundle metadata now includes a long description and copyright line. Previously the bundle config had no icon at all, which would have failed `tauri build` independently of the WebKitGTK blocker below.
- `.github/workflows/ci.yml` gained a `desktop` matrix job that runs `scripts/build-sidecar.sh` and `cargo check` natively on `ubuntu-latest`, `windows-latest`, and `macos-latest` for every push/PR. `scripts/build-sidecar.sh` was made to resolve `pyinstaller` from `PATH` first so it works in a plain CI `pip install`, not only inside this repo's own `.venv`.
- **Linux WebKitGTK/GLib dependencies are now installed on this workstation** (`libwebkit2gtk-4.1-dev`, `libjavascriptcoregtk-4.1-dev`, `libgtk-3-dev`, `libsoup-3.0-dev`, `libayatana-appindicator3-dev`, `librsvg2-dev`, `build-essential`), so `cargo tauri build` runs natively here, not only in CI.
- **A real `tauri build` was run and produced installable Linux artifacts**: `.deb`, `.rpm`, and `.AppImage`, all at 0.1.0. This is the first time this repository's actual bundling pipeline (as opposed to `cargo check`) was exercised end to end, and it surfaced two real bugs that only a genuine build+launch could catch:
  - `beforeDevCommand`/`beforeBuildCommand` in `tauri.conf.json` ran with cwd already set to `frontend/` (Tauri resolves hooks relative to `frontendDist`'s parent), so the old `npm --prefix frontend run build` looked for `frontend/frontend/package.json` and failed. Fixed to plain `npm run build`/`npm run dev`.
  - `tauri_plugin_updater::Builder::new().build()` was registered unconditionally in `src-tauri/src/lib.rs`, which panics `app.build()` at startup ("invalid type: null, expected struct Config") because `tauri.conf.json` has no `plugins.updater` block — there is no real signing identity yet. The registration is now commented out with an explanation, rather than shipping a fake placeholder key; the `tauri-plugin-updater` Cargo dependency is kept so re-enabling it later (once `docs/releasing.md`'s signing step is done) is a one-line change.
- **Fixed a real sidecar orphan-process bug**, found by launching the packaged binary and killing it: the PyInstaller onefile bootloader forks a second process (the actual Python interpreter) that inherits the bootloader's process group rather than getting its own. The old cleanup path only killed the single tracked child PID (the bootloader), leaving the real worker process running indefinitely after the app closed — true both for a raw `SIGTERM`/`SIGINT` (`kill`, systemd stop, session logout — previously not handled at all) and, since both paths shared the same single-PID kill, very likely also for the normal "close window" path. Fixed in `src-tauri/src/lib.rs`: a `ctrlc` handler now also runs on `SIGTERM`/`SIGINT`, and the shared `kill_backend()` helper signals the sidecar's whole process group (`libc::getpgid`/`libc::kill(-pgid, SIGTERM)`) on Unix before falling back to the single-PID kill. Verified with three separate launch→health-check→SIGTERM cycles (raw binary and the actual `.AppImage`): `ps` shows zero remaining `ai-linkedin-*` processes after each one.
- **Ran the `docs/packaging.md` smoke checklist against the real `.AppImage` on this machine**: launched without any manually-started Python/PostgreSQL/Redis (the running `ai_linkedin_manager-postgres-1`/`-redis-1` dev containers on this box were never touched by the packaged app — desktop mode uses only SQLite); reached authenticated readiness (`GET /health` → 200, `GET /runtime/bootstrap` → 401 without the launch token, as designed); SQLite migration ran cleanly to a fresh `app-data` directory (`database/app.sqlite3` created, `state/runtime.sqlite3` + `-wal`/`-shm` confirming WAL mode); provider-client modules (Anthropic/OpenAI/Composio SDKs) imported successfully inside the frozen binary (the process would have failed to start otherwise); closing it left no orphan process and unmounted its FUSE mount. Not yet exercised: an actual credential round-trip through the OS keyring, RAG ingest/retrieve, or approval gating through the UI (no browser/webview automation was used — only HTTP probes against the loopback API), and upgrade/rollback/uninstall (no version-to-version upgrade was tested, and the `.deb`/`.rpm` were built but not installed via `dpkg`/`rpm`).

## Release prerequisites outside this workstation

- Windows and macOS sidecars/installers must still be built and smoke-tested end-to-end (`tauri build`, install, launch, migrate, uninstall) on native runners or real machines. CI's `desktop` job proves the shell compiles there; the orphan-process fix above is Unix-only (`#[cfg(unix)]`) and explicitly still needs its own validation on a native Windows runner — Windows has no direct equivalent of a POSIX process group and would need a job-object-based fix, not yet written.
- Production artifacts still require platform signing/notarization identities and Tauri updater signing keys — deliberately not generated by this session, since production signing-key custody is the repository owner's decision, not something to invent from a coding session. SBOM/license review and upgrade/rollback/uninstall drills (via the actual `.deb`/`.rpm` installers, not just the portable AppImage) are also still outstanding.
- Native keyring behavior must be exercised in real Windows Credential Manager, macOS Keychain, and supported Linux Secret Service sessions — this session confirmed the app *starts* with the OS-keyring credential backend selected in desktop mode, not that a saved credential round-trips through it.
- Active tag/push release automation is intentionally absent until the repository owner explicitly authorizes workflows that publish external releases. The `desktop` CI job only compiles; it does not build, sign, or publish installers.

Until those prerequisites are completed, version 0.1.0 is a validated desktop development build — with a real, working Linux `.deb`/`.rpm`/`.AppImage` produced and smoke-tested this session — not a signed production release.
